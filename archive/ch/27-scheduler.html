QoS、队列与调度意图

用系统提供的并发抽象表达工作优先级，而非自行假设执行顺序

QoS（Quality of Service）描述工作的相对重要程度，帮助系统在响应性、能耗和资源分配之间作出调度决策。它不是实时期限，也不保证某个线程何时运行。

从任务到执行

应用把工作提交到队列或并发 API；系统结合 QoS、线程可运行状态、设备负载与电源状态安排执行。主线程承担 UI 响应，耗时 I/O、解码和计算不应阻塞它。队列是组织任务的抽象，不等于一个永久专属线程。

心智模型
应用表达意图 → 调度系统评估上下文 → 工作在可用资源上执行。不要将“并发”误读为“并行”，也不要依赖未记录的线程顺序。

QoS 使用原则

  • 用户正在等待的短任务可采用适当的用户交互优先级；可延迟的维护工作使用较低优先级。
  • 避免无依据地提高优先级，否则会增加能耗并挤占系统资源。
  • 保持依赖关系清晰，避免高优先级工作等待低优先级任务造成优先级反转。
  • 用结构化并发、OperationQueue 或 GCD 管理生命周期和取消，不手工制造线程池。

实验：观察而不是猜测

  1. 在自有样例中创建短时计算任务与 UI 更新任务，记录所用队列、QoS 和设备状态。
  2. 用 Instruments 的 Time Profiler / System Trace 观察主线程阻塞、任务等待与 CPU 使用。
  3. 改变任务优先级或取消策略，比较响应时间和能耗；每次只改变一个变量。
  4. 写明设备、OS、构建优化级别和测量误差，不把单次结果推广为调度保证。

常见误区

线程数等于 CPU 核数、异步必定更快、后台队列永不阻塞，都是不成立的假设。优先从算法复杂度、批处理、缓存和取消能力入手优化。
