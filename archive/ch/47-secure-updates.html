S08

更新、配置与安全回滚

配置能改变行为，所以它必须像代码一样被校验和回滚

远程配置让产品不必发版就能调整行为，也因此成为一条影响全量用户的通道。安全设计要回答：谁能改、改动能到哪、错了怎么退。

1. 能下发什么

内容可以做不可做
功能开关按人群、版本、地区开启作为业务授权的唯一依据
文案与资源替换展示内容、图片借资源路径加载可执行内容
参数与阈值调整超时、批量大小传入未校验的值直接参与敏感计算
可执行代码平台通常不允许动态下发任何形式的“热更新代码”

最后一行是硬约束：绕过平台规则下发可执行逻辑，既有审核风险，也让完整性无法保证。

2. 治理要点

  • 完整性：配置应通过受信通道获取，必要时校验签名或哈希。
  • 类型与范围：解码后逐字段校验，拒绝越界值与未知枚举。
  • 默认值：本地必须有可用默认值，配置缺失时行为可预测。
  • 灰度：先小比例、可观测，再扩大；避免一次性全量。
  • 过期：配置有生效期与失效期，避免历史值长期残留。
Swift：解码后做范围校验
struct RemoteConfig: Decodable {
    let timeoutSeconds: Int
    let maxRetry: Int
}

func validate(_ config: RemoteConfig) throws {
    guard (5...60).contains(config.timeoutSeconds) else { throw ConfigError.outOfRange }
    guard (0...3).contains(config.maxRetry) else { throw ConfigError.outOfRange }
}

3. 失败与回滚

场景期望行为
拉取失败使用本地缓存或默认值，不阻塞启动
配置非法整份拒绝或回退到上一份有效配置
新配置导致异常服务端开关关闭，客户端回到安全默认
版本不兼容按版本下发不同配置，旧版本保持可用

“安全默认”要在设计时就定好：关闭高风险功能、保持只读、提示用户稍后再试，而不是默认放开。

4. 审计

  • 每次配置变更记录：谁改的、改了什么、影响范围、审批人、时间。
  • 客户端上报生效配置的版本号，出现问题时能确认影响面。
  • 敏感开关（涉及权限、支付、隐私）变更需要双人确认。

5. 可验证实验

  1. 构造越界与错误类型的配置，确认客户端拒绝而不是崩溃或使用异常值。
  2. 断开网络启动应用，确认默认值生效且功能可用。
  3. 下发一份“会导致异常”的配置（在自有测试环境），演练服务端关闭开关后的恢复时间。
