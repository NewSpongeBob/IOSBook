公开 API、受限 API 与兼容性

公开、受限与未公开 API 的区别，本质是“谁向你承诺了兼容性”

平台 API 分三类：公开且承诺兼容的、需要能力或授权才能使用的、未公开且不承诺任何东西的。第三类会给上架与稳定性带来直接风险，前两类则需要按系统版本设计降级。

1. 三类 API

类别典型来源兼容承诺风险
公开 API系统框架公开头文件与文档有，按版本演进并标注弃用低，但需处理可用性差异
受约束 API需要 entitlement、审核批准或特定分发方式有，但前提是具备资格中，能力缺失时功能不可用
未公开 API符号存在于二进制但无文档无高：随时变化、审核拒绝、行为不可预期

判断标准不是“能不能调用成功”，而是“有没有人向你承诺下次仍然这样”。用反射或动态查找绕过编译检查，得到的只是“当前版本能跑”。

2. 可用性检查的正确写法

按系统版本分支，而不是按设备猜测
if #available(iOS 17, *) {
    useNewAPI()
} else {
    useFallbackPath()
}
  • 编译使用的 SDK 版本与运行设备的系统版本是两个维度，二者都要考虑。
  • 弱链接符号在旧系统上可能不存在，调用前必须有可用性判断。
  • 不要用 responds(to:) 作为版本判断的主要手段：它能告诉你对象是否实现某方法，但不能告诉你语义是否相同。

3. 弃用不是失效

弃用表示“计划移除、建议迁移”。迁移窗口内旧 API 往往仍可用，但新系统上可能行为不同。工程上的做法是把弃用当作待办事项进入技术债清单，而不是等编译警告堆积后一次性处理。

4. 受限 API 的合规路径

某些能力只对特定类型的应用开放，需要申请并在审核中说明用途。合规路径的要点是：能力与功能一一对应、用途可解释、失败有降级。绕开申请使用未公开手段，短期可行但会带来下架与兼容风险。

5. 可验证实验

  1. 对同一份自有代码在多个系统版本的模拟器上运行，记录可用性分支的实际走向，确认没有“只在最新版本测过”的路径。
  2. 把某处 #available 判断故意写错（例如用错版本号），观察在旧系统上的失败形态，理解为什么需要测试矩阵。
  3. 对自己依赖的第三方库检查其使用的 API 是否有弃用警告，评估升级成本。

6. 版本策略

  • 维护一张“最低支持版本 → 关键能力 → 降级方案”的表，随版本更新。
  • 把系统版本纳入缺陷分级：只在旧版本出现的问题，同样需要回归。
  • 灰度发布时观察异常率与版本分布，避免把新系统特有问题误判为服务端问题。

自测

  1. 为什么“调用成功”不能证明使用公开 API 是安全的？
  2. SDK 版本与设备系统版本在什么情况下会造成“编译通过、运行崩溃”？
  3. 受约束 API 的能力缺失时，产品应如何设计降级？
