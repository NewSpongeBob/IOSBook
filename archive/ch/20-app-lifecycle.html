06

应用生命周期与场景

前台、后台、挂起与被终止，是四种不同的可用性假设

生命周期不是一组回调的名字，而是“系统允许你做什么”的集合。多数线上问题来自把“进入后台”当成“还能继续跑”，或把“挂起”当成“进程已退出”。

1. 状态与场景

状态能做什么系统可能做什么
未运行无无
前台活跃正常执行、渲染、接收用户输入受主线程响应性与内存限制约束
前台非活跃短暂过渡（来电、控制中心、切换中）可能不派发触摸事件
后台有限时间与有限能力到时挂起或终止
挂起无执行，内存保留内存紧张时直接终止，不再回调

引入场景（scene）后，一个进程可以有多个界面实例，生命周期回调从“应用级”扩展到“场景级”。做状态判断时先问：这是进程的状态，还是某个界面的状态？两者在分屏、多窗口与外部显示场景下并不一致。

2. 后台不是“继续运行”

  • 进入后台后获得的执行时间用于收尾，不是常驻许可。
  • 需要延后执行的工作交给系统的后台任务调度，由系统决定何时运行，执行时长不保证。
  • 持续后台能力（音频、定位、通话等）需要相应能力声明，并被审核与用户可见性约束；滥用会导致耗电与上架风险。

3. 三种“被结束”

  1. 崩溃：有崩溃报告，可符号化定位。
  2. 看门狗终止：启动或主线程长时间无响应，系统主动结束进程，报告形态与崩溃不同。
  3. 内存压力终止：挂起状态下被回收，通常没有应用侧回调。

三者常被用户统一描述为“闪退”。排查时先按报告类型分类，再看时间线，否则容易在错误方向上加日志。

4. 生命周期里的安全时机

进入后台时，系统会为应用生成界面快照用于切换动画。如果界面上有敏感信息，这张快照会留在系统缓存中。正确做法是在进入非活跃状态时立即遮挡敏感内容：

SwiftUI：用场景阶段遮挡敏感界面
@Environment(\.scenePhase) private var phase
@State private var masked = false

var body: some View {
    content
        .overlay { if masked { Rectangle().fill(.regularMaterial) } }
        .onChange(of: phase) { _, newValue in
            masked = newValue != .active
        }
}

上面的 onChange 双参数形式自 iOS 17 起可用，旧版本需使用单参数重载或代理回调；写示例时要标注适用系统版本。

同类时机还有：锁屏后受保护文件不可读、生物识别在后台不可用、令牌刷新失败需要重新认证。把这些当作状态机的分支，而不是异常兜底。

5. 可验证实验

  1. 在自有样例中用统一日志记录每次状态与场景切换，包含时间戳与原因；反复前后台切换，检查是否出现“只收到进入后台、没有回到前台”的异常序列。
  2. 在后台触发一次耗时收尾，观察系统给的时间窗；把耗时人为放大，记录被终止时的报告类型。
  3. 构造大内存占用后挂起，用开发者工具观察内存压力与终止，比较“主动释放”和“被回收”的差异。
