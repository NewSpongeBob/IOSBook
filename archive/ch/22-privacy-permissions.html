08

隐私权限与用户同意

权限状态是可查询、可变化、可被拒绝的产品状态，不是一次弹窗

隐私权限不是“申请一次就通过”的开关，而是四种以上状态的组合，且用户随时可以在设置里改变。把权限当成布尔值，是隐私相关崩溃与体验问题的常见根因。

1. 状态的完整集合

状态含义应用侧应对
未决定尚未请求过在合适的上下文中发起请求
已拒绝用户明确拒绝，或此前拒绝后系统不再弹窗解释影响，提供跳转设置的路径
受限被家长控制或设备策略限制不引导用户改设置，直接降级
已授权可使用正常功能
部分授权如相册“仅选中的照片”、位置“大致位置”按范围处理，不假设全量可访问

“已拒绝”与“受限”的差别很重要：前者用户可改，后者改不了。把受限当拒绝去引导用户设置，会让用户困惑。

2. 请求时机与用途说明

  • 系统弹窗里展示的用途说明来自工程配置，必须具体：说清“用来做什么”，而不是“为了更好的体验”。
  • 请求应出现在用户能理解其必要性的时刻。启动即连环弹窗会显著降低授权率。
  • 被拒绝后不要反复弹窗——系统不会再显示，重复请求只是无效调用。

3. 降级路径才是产品能力

权限被拒时，功能应退化而不是中断。例如相册受限时允许用户逐张选择、位置降级为手动输入城市、通讯录不可用时允许手工填写。降级路径要能在测试中被稳定触发，否则等于没做。

处理相册“部分授权”
let status = PHPhotoLibrary.authorizationStatus(for: .readWrite)
switch status {
case .authorized:
    loadAllAssets()
case .limited:
    loadSelectedAssets()   // 仅用户选中的资源
case .denied, .restricted:
    showManualPickerHint()
case .notDetermined:
    await PHPhotoLibrary.requestAuthorization(for: .readWrite)
@unknown default:
    showManualPickerHint()
}

@unknown default 不是形式主义：新系统可能新增状态，漏掉会让旧代码走进未定义分支。

4. 敏感数据面不止权限 API

  • 日志与遥测：权限之外的泄漏常发生在日志、崩溃报告与分析事件里。
  • 剪贴板：读取可能触发系统提示，也可能包含用户无意复制的内容。
  • 通知内容：锁屏展示的信息是否包含敏感字段，应由产品明确决定。
  • 跨应用追踪：需要单独的授权，且不应通过指纹式信号绕过。

5. 可验证实验

  1. 在自有应用中逐项查询并记录权限状态，切换系统设置后重新查询，确认代码能正确响应变化（不要缓存首次结果）。
  2. 构造“拒绝”“受限”“部分授权”三种状态，验证降级路径可用且无崩溃。
  3. 检查一段包含业务字段的日志，确认没有用户名、令牌、位置坐标等不应出现的内容。

自测

  1. 为什么“已拒绝”和“受限”需要不同的产品文案？
  2. 部分授权为什么要求代码显式处理，而不能当作“已授权”？
  3. 权限已授予，是否意味着可以随意记录相关数据？
