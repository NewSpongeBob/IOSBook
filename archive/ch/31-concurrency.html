K08

并发正确性与资源管理

并发缺陷有分类，先定性再选工具

并发问题之所以难，是因为失败往往依赖时序。把缺陷先分类，再选择隔离方式与检测工具，比泛泛地“加锁”更有效。

1. 五类问题

类别表现根因
数据竞争结果偶发错误、崩溃无同步的并发读写
死锁永久卡住循环等待或锁顺序不一致
活锁/饥饿一直重试但无进展策略导致某些任务永远拿不到资源
优先级反转高优先级任务被拖慢等待低优先级持有的锁
资源泄漏描述符或任务累积异常路径未释放、取消未生效

2. 先选隔离，再加锁

锁是最容易想到也最容易出错的手段。优先级更高的设计是减少共享：

  • 值语义：传递不可变副本，天然不存在并发写。
  • 串行执行器：把状态限定在一个执行上下文，外部只能提交请求。
  • actor 隔离：把状态与操作绑定，跨隔离访问必须经过异步消息。
  • 锁：用于确实无法隔离的共享，且锁内不做 I/O、不调用未知回调。
actor 把状态收敛到单一隔离域
actor Cache {
    private var storage: [String: Data] = [:]

    func value(for key: String) -> Data? { storage[key] }
    func store(_ data: Data, for key: String) { storage[key] = data }
}

跨隔离访问自动变为异步调用，编译器会阻止直接读写内部状态。代价是你要处理等待与重入，而不是显式加锁。

3. 取消与结构化并发

  • 取消是协作式的：任务需要在检查点主动退出，否则取消只是“标记”。
  • 父任务等待子任务结束，取消沿任务树传播；不要让子任务脱离作用域无限存活。
  • 不能用取消来保证资源释放——释放应写在作用域退出路径上。

4. 资源生命周期

文件描述符、socket、观察者、定时器、图像解码缓冲都有明确的关闭动作。设计要点：

  • 使用“作用域结束即释放”的结构，而不是依赖对象析构的时机。
  • teardown 要幂等，允许重复调用；异常路径也必须走到。
  • 在退出登录、切换账号、进入后台等业务节点显式清理，而非只依赖释放。

5. 工具与实验

  1. 用线程检查工具对自有样例跑一遍完整测试，记录报告；修复后确认报告消失且功能未变。
  2. 构造一个死锁（两把锁、相反顺序），采样卡住的线程栈，确认能凭栈判断锁顺序问题。
  3. 让一个任务在取消后继续运行，观察资源是否被正确释放，验证“取消不等于清理”。
  4. 用日志记录任务开始/结束与队列标识，重现一次偶发错误的时间线。
