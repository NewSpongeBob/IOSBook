H03

设备与系统版本测试矩阵

矩阵的目的不是穷举，而是让未覆盖的部分变成明确的已知

测试矩阵是“在有限资源下，用哪些组合覆盖风险”的声明。它的价值一半在选取，一半在说明没选什么。

1. 维度

维度取值示例影响什么
设备代际老款小内存、主流、最新内存、性能、传感器能力
系统版本最低支持、主流、最新API 可用性、权限模型
架构设备 64 位、模拟器指令、符号、平台字段
授权状态未决定/拒绝/受限/部分授权降级路径
网络弱网、断网、切换超时、重试、幂等
存储状态全新安装、覆盖升级、空间不足迁移、缓存、错误处理

2. 组合爆炸怎么裁

  1. 风险驱动：影响资金、隐私、授权的路径优先覆盖。
  2. 等价类：同一系统大版本内的相邻小版本通常可合并，除非有已知差异。
  3. 用户分布：按真实活跃设备的版本与机型分布分配比重，而不是平均分配。
  4. 两两组合：不做全组合，至少覆盖“最低版本 + 最弱设备”“最新版本 + 最新设备”两端。

3. 记录模板

一个可复用的用例记录
用例：后台刷新时令牌过期
设备：iPhone SE (第 2 代) / iOS 16.x
构建：1.4.2 (482)
步骤：登录 → 切后台 → 等待 12 小时 → 触发刷新 → 回前台
预期：静默刷新成功；失败则提示重新登录且不丢草稿
证据：时间线日志 + 截图（脱敏）
结论：通过 / 失败 / 阻塞（写明原因）

4. 未覆盖声明

报告里应明确写出：本版未测试的机型与系统版本、未构造的异常状态、已知但不修的问题。没有这句话，读者会默认“全都测过”。

5. 维护

  • 系统大版本发布前更新矩阵，而不是发布后补救。
  • 每次线上事故反问：这个组合是否在矩阵里？不在就补上。
  • 删除长期无差异的组合，把资源挪到高风险路径。

自测

  1. 为什么测试矩阵需要“未覆盖声明”？
  2. “两两组合”解决了全组合爆炸中的什么问题？
  3. 线上事故如何反向改进矩阵？
