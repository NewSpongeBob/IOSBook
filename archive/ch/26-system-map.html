系统组件地图与启动后服务

从内核到主屏，找到“这个功能由谁负责”的地图

排查 iOS 问题时，最常见的低效是“在应用里找系统的问题”。建立一张组件地图，可以快速定位责任层，避免在三层之外猜原因。

1. 分层地图

层代表组件典型职责
内核XNU、驱动、文件系统调度、内存、I/O、IPC 原语
系统服务launchd 管理的守护进程生命周期、网络配置、凭据、通知分发
界面服务负责显示与事件的服务进程、主屏服务输入事件、窗口合成、应用切换
框架Foundation、UIKit/SwiftUI、Core* 系列把系统能力包装成 API
应用你的进程与扩展业务逻辑、界面、数据

守护进程的名字与分工随版本调整，不要把某个具体进程名当成永久事实；要记住的是“存在哪几类职责”。

2. 一次点击经过谁

  1. 触摸硬件产生事件，由系统事件服务分发。
  2. 窗口服务确定命中哪个应用的哪个窗口，并处理切换与动画。
  3. 你的进程收到事件，框架把它转成手势或控件回调。
  4. 界面更新被编码为绘制指令，由渲染相关服务合成到屏幕。

因此“点击无响应”至少有四种可能：硬件/事件层、窗口层、应用主线程、渲染层。只看应用日志往往只能覆盖第三种。

3. 观察手段

  • 统一日志：按 subsystem 与 category 过滤，能看到跨进程的时间线；注意隐私字段默认被隐去。
  • 系统诊断包：包含进程列表、日志、崩溃与资源信息，是事后分析的主要材料。
  • 性能工具：观察主线程、系统调用、线程状态，比猜测更可靠。
  • 模拟器命令行：可以查看进程与启动配置，但模拟器没有真实设备的安全组件与部分服务。
模拟器中查看进程与启动项
xcrun simctl spawn booted launchctl list | head -30
xcrun simctl spawn booted ps -A -o pid,comm | head -30

4. 从现象到层

现象优先怀疑证据来源
启动即退出、无界面应用初始化或签名/能力崩溃报告、启动日志、签名信息
界面卡住但进程存活主线程阻塞或渲染压力性能工具、堆栈采样
网络偶发失败连接复用、策略配置或服务端网络日志、客户端错误码分布
后台被终止内存压力或时间预算超限系统诊断、终止原因字段
跨应用共享数据异常访问组配置或写入竞争签名能力、文件时间线

5. 可验证实验

  1. 在自有样例中制造“主线程阻塞”和“后台大量内存占用”，分别收集诊断材料，比较报告中的关键字段差异。
  2. 用统一日志把一次完整的用户操作串起来，标注每一步发生在哪个进程，形成自己的时序图。
  3. 把同一功能在模拟器与真机上各跑一次，列出行为差异（安全组件、性能、服务可用性），形成“不可在模拟器验证”的清单。
