S01

威胁建模与防护验证

先明确“保护什么、防谁、被攻破后会怎样”，再谈措施

威胁建模不是写一份文档，而是把“资产、边界、攻击者能力、授权范围”四件事说清楚，让后续每一项测试都有对应的问题。没有模型的检测清单，只是在碰运气。

1. 四个输入

输入要回答的问题典型产出
资产哪些数据与操作有价值？数据分级表、关键操作清单
信任边界数据在哪里换了“信任等级”？数据流图上的边界标注
攻击者能力能接触设备、网络、构建链的哪一环？能力假设与不在范围内的攻击
授权范围测试允许做什么、不允许做什么？书面范围与停止条件

四项里最容易缺的是最后一项。范围不清时，技术越强越危险。

2. 画一条数据流

  1. 采集：用户输入、设备信息、权限数据。
  2. 传输：通道、证书校验、重试与缓存。
  3. 存储：容器文件、钥匙串、偏好设置、内存缓存。
  4. 旁路：日志、分析事件、崩溃报告、通知内容、界面快照。
  5. 删除：注销、切换账号、卸载时的清理。

多数泄漏不在主链路，而在旁路：一条调试日志、一次崩溃上报、一个备份文件。建模时把旁路画出来，测试才有落点。

3. 控制措施的分层

层能做什么不能做什么
客户端加固提高逆向与篡改成本形成信任边界
平台机制沙盒、数据保护、签名、权限替代业务授权
服务端授权按身份与上下文判定保护已下发到客户端的数据
传输保护防窃听与篡改防客户端自身被控制
监控与响应发现异常、限制影响事后修复已泄漏的数据

4. 从威胁到用例

以“访问令牌泄漏”为例，把它拆成可执行测试：

  • 令牌是否出现在日志、崩溃报告、分析事件中？
  • 是否被写入可备份位置？换机恢复后是否仍有效？
  • 锁屏状态下能否被读取？读取失败时是否有降级？
  • 服务端是否校验令牌的设备绑定、有效期与权限范围？
  • 注销后令牌是否被撤销，而不只是本地删除？

5. 验证计划模板

一次评估的最小记录
范围：仓库 / 构建号 / 测试设备 / 测试服务 / 明确禁止项
假设：攻击者能力、已排除的攻击
用例：编号 + 步骤 + 预期失败形态
证据：截图、日志片段、报告（脱敏）、时间戳
结论：事实 / 推断 / 未知（分别标注）
状态：通过 / 失败 / 需复测 + 责任人

6. 边界说明

只对自有或明确授权的目标
所有动态验证限于自建应用、模拟器、自有测试服务与虚构数据。发现的问题按内部流程处理，不在公开渠道披露他人的实现细节。

自测

  2. 客户端加固为什么不能作为授权边界？
  3. 一条威胁如何拆成可执行、可复现的测试用例？
