S05

隐私、日志与遥测

“只是调试日志”不是理由，副本一旦产生就要按数据对待

日志与遥测的价值在于排障与决策，代价是数据的第二份、第三份副本。设计时要同时回答：谁需要这份数据、保留多久、出错时会不会把敏感字段带出去。

1. 数据面盘点

位置常见风险基本控制
调试日志打印请求头、令牌、完整响应字段白名单、默认脱敏
崩溃报告异常信息夹带用户输入清理自定义字段、限制附加信息
分析事件自由文本字段被塞入隐私数据结构化字段 + 枚举值
通知内容锁屏可见敏感信息摘要化、可选隐藏正文
界面快照后台切换缓存含敏感界面非活跃状态遮挡
剪贴板敏感内容被其他应用读取避免复制、及时清理、提示

2. 日志的三条原则

  • 结构化：用固定字段承载可枚举的信息，避免把整段 JSON 拼进消息字符串。
  • 白名单：默认不记录，明确列出需要记录的字段；黑名单永远漏项。
  • 可关联但不识别：需要串联同一用户的操作时，用服务端生成的短生命周期标识，而不是手机号或邮箱。

3. 平台日志的隐私标注

统一日志系统支持对动态值标注隐私级别。默认策略下，字符串常常被隐去，这正是“本机看着有、导出的日志里全是占位符”的原因。

Swift：区分公开与私有字段
import os

let logger = Logger(subsystem: "com.example.app", category: "auth")
logger.info("sign-in attempt account=\(account, privacy: .private) result=\(result, privacy: .public)")

把结果与状态码标为公开、把账号等标识标为私有，既保留可诊断性，又避免把身份写进日志。调试期需要明文时，应在受控环境临时开启，并确保该设置不进入发布构建。

4. 保留与删除

  • 按用途设定保留期限：调试日志以天计，聚合指标以月计。
  • 为“删除请求”准备可执行路径：本地缓存、分析平台、崩溃收集器都要覆盖。
  • 明确哪些数据不出境、不出第三方，并在隐私声明中与实际一致。

5. 可验证实验

  1. 在自有应用中触发几条包含账号与令牌的日志，导出系统日志，检查这些值是否可见。
  2. 构造一次崩溃，查看报告的附加信息字段，确认没有用户输入被带入。
  3. 审计一个分析事件的定义，列出每个字段的取值来源，删除非必要字段。

6. 事件响应时的取舍

事故中希望“日志越全越好”，但事后无法收回。可行做法是提前定义“可临时提升的诊断开关”：有范围、有期限、有审批，且只在受控环境生效，而不是长期全量记录。
