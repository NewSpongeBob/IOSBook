F05

兼容与检测面

能跑起来只是第一步，能解释“为什么这台不行”才算会用

插桩工具对系统版本、架构与签名状态很敏感。同一份脚本，在不同设备上可能一个正常、一个直接崩溃；防御方看的也主要是这几类差异。

1. 兼容矩阵

维度影响排查方式
系统版本运行时结构、加载器行为、内存布局固定版本复现，逐版本对比
架构arm64 与 arm64e 的签名/跳转校验不同确认设备架构与工具支持
签名状态决定能否加载额外代码调试能力与设备状态
工具版本agent 与宿主协议需匹配两端版本对齐

2. 典型不兼容

  • 加载器变化：新系统改了镜像布局，旧的注入偏移失效。
  • 指针认证：伪造跳转目标被拒，表现为异常而不是“没效果”。
  • 端口冲突：默认端口被占用或已被改，连接超时。
  • 应用加固：完整性校验或反调试让进程在注入后立刻退出。

3. 检测面：可改的与难改的

信号怎么被发现可靠性
监听端口扫描本机端口，常见 27042 / 27043中：端口可改
额外线程线程列表出现非应用创建的线程中：线程名可伪装
模块列表镜像中出现未随包分发的库高：需真实加载
可执行映射出现未签名的可执行内存段高
环境变量启动参数中出现注入变量中
时序异常关键路径耗时显著变长低：易误报
先看“能不能”，再看“像不像”
“端口在监听”只能说明有服务；“模块列表里多了一个库”才能说明代码被加载。判断可靠性时优先看后者。

4. 命令形态

确认工具与设备的匹配情况
frida --version                 # 本机工具版本
frida-ps -U                     # 列出设备上的进程（能列出说明通道可用）
frida-ps -Uai | grep -i yourapp # 只看自己的应用
lsof -nP -iTCP:27042 -sTCP:LISTEN   # 端口是否被占用

5. 评估自己的防护

  1. 列出你能观测的信号，标注每条的证据来源。
  2. 在正常设备上跑一遍，统计误报——这是最容易被忽略的成本。
  3. 假设某条信号失效，看是否还有其它层能兜住。
  4. 把结论写进发布检查，而不是停留在“我们加了检测”。

6. 失败分流

现象原因查哪里
某版本必崩运行时结构变化按版本二分，缩到具体 API
某机型失效架构差异（arm64e）核对架构与工具支持
注入后应用退出完整性或调试检测崩溃报告、检测分支
连接超时端口被占用或转发错误实际监听端口
脚本语法通过但不执行运行时版本不支持该 API工具与 agent 版本

7. 数据细节：兼容矩阵有多大

维度取值说明
系统版本最低支持 / 主流 / 最新至少三档
架构arm64 / arm64e指针签名差异
环境真机 / 模拟器模拟器无真实签名与 SEP
合计约 12 格全测成本高，需按风险裁剪

裁剪原则：功能强相关（签名、内存、注入）的格子必须测；与平台无关的纯业务逻辑可合并。

8. 一次真实排查记录：某系统版本必崩

  1. 现象：同一份脚本，最新系统正常，次新系统一注入就崩。
  2. 先切片：按“系统版本 × 架构”二分，确认是版本相关还是机型相关。
  3. 缩到调用：在崩溃前最后一个成功回调处停下，看下一个调用的参数。
  4. 换路径：该版本可能改了运行时结构，改用不依赖内部布局的接口。
  5. 结论与限制：记录“该版本结构变化”，并注明结论只对该版本区间成立。
实机输出：记录环境所需的最小信息
ProductName:		macOS
ProductVersion:		15.7.5
BuildVersion:		24G624

读法：兼容结论必须带版本号 + 构建号。15.7.5 是市场营销版本，24G624 才是构建标识；只写前者，两台机器可能不是同一构建。
