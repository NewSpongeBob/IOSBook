X01

分析对象、工作台与证据

先确定“分析谁、为什么分析、证据怎么留”，再打开工具

逆向工程在本书里的定义很窄：在自己构建的应用、自己的设备与公开样本上，用工具建立可复现的观察，回答“它是怎么工作的”。它不包含绕过他人保护、修改他人产物或分发破解版本。

1. 三类对象，三类动作

对象允许的动作前提
自己构建的应用反汇编、调试、插桩、修改后重签使用测试账号与虚构数据
自己的测试设备 / 模拟器抓包、日志、性能跟踪、安装调试构建不接入生产环境与他人账号
公开样本与开源代码阅读、对比、学习结构遵守许可证，不用于攻击他人
他人应用 / 线上服务不在本书范围需书面授权，且遵守法律

2. 工作台

工具用途备注
Xcode / Instruments构建、运行、性能与内存观察调试构建才有完整符号
lldb断点、查看对象与内存、调用栈需要可调试的签名
otool / nm / dyld_info文件结构、依赖、符号随 Xcode 提供
反汇编器（Hopper、IDA、Ghidra）阅读函数、交叉引用、调用图先看符号，再看地址
插桩框架在运行时观察/替换自有方法只对自己构建的应用使用
代理工具观察自有测试服务的请求仅自有域名与测试账号

工具不是门槛，环境隔离才是：单独一台测试机、独立测试账号、独立测试服务，出问题不影响真实用户。

3. 证据规范

每次分析至少留这六项
对象：应用名 + 构建号 + 产物哈希
环境：设备型号 / 系统版本 / 是否模拟器
目标：这次要回答的具体问题
手段：工具与命令（含版本）
观察：原始输出、截图、地址与符号
限制：结论适用范围与不确定项

4. 推荐的推进顺序

  1. 静态侦察：先弄清产物由什么组成、有哪些名字可用（X02）。
  2. 运行时观察：用调试器确认调用顺序与真实参数（X03）。
  3. 反汇编阅读：当符号不够用时，看指令层（X06、X07）。
  4. 插桩验证：用可控改动验证假设，而不是猜测（X04）。
边界
涉及第三方应用的破解、绕过检测、去除保护步骤，本书不提供。X08 只讨论如何识别防护与评估自己防护的有效性。

自测

  1. 为什么“只分析自己的应用”既是合规要求，也是学习效率更高的选择？
  2. 证据里为什么必须记录产物哈希与构建号？
  3. 静态侦察与运行时观察各自能回答什么问题？
