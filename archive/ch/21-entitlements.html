Entitlements 与能力授权

entitlement 是签名声明的能力，不是用户授权，更不是业务权限

entitlement 描述“这个签名的应用被允许使用哪些系统能力”。它由签名与描述文件共同约束，安装与启动时被校验。它不等于用户同意，也不能替代服务端授权。

1. 常见能力与其来源

能力解决的问题谁能授予
应用标识确定应用身份与归属团队开发者后台 + 签名
钥匙串访问组限定能共享凭据的应用/扩展范围开发者后台 + 签名
推送环境区分开发与生产推送通道证书与描述文件
关联域声明可代理的通用链接域名开发者后台 + 服务端文件
调试附加允许调试器附加到进程开发构建，发布构建应移除

注意最后一行：调试能力只应存在于开发构建。发布包若残留该能力，等于把进程开放给附加调试，属于典型的构建配置事故。

2. 缺失能力时的表现

不同能力的失败形态不一样：有的在调用时返回权限错误，有的直接让功能不可用，有的在安装阶段就被拒绝。共同点是错误信息通常不会明确告诉你“缺哪个 entitlement”，需要回到签名与描述文件核对。

核对构建产物实际携带的能力
codesign -d --entitlements :- /path/to/YourApp.app 2>&1
# 关注 application-identifier、keychain-access-groups、aps-environment、get-task-allow

3. 三种“权限”不要混用

  • entitlement：编译与签名期确定，回答“能不能用这个能力”。
  • 用户授权：运行时由用户决定，回答“用户是否允许这次访问”。
  • 业务授权：由服务端依据身份与上下文判定，回答“这个用户能不能执行这个操作”。

把业务授权放在客户端——无论用 entitlement、越狱检测还是字符串混淆——都只是提高成本，不构成信任边界。客户端的一切都可被观察，判定必须在权威端完成。

4. 可验证实验

  1. 分别对 Debug 与 Release 构建查看 entitlements，列出差异并解释每一项为什么存在。
  2. 在自有应用中用 group 标识创建共享存储，然后在签名中移除对应能力，记录访问返回的结果。
  3. 检查关联域配置：域名侧的文件是否可访问、内容是否与工程配置一致，验证“声明”与“实际可用”是否一致。

5. 发布检查

  • 能力集合与产品功能一一对应，没有历史遗留项。
  • 推送环境与发布通道匹配，扩展与主应用能力一致。
  • 发布构建不含调试附加能力。
  • 能力相关的失败路径有产品级降级方案，而不是直接崩溃。

自测

  1. 为什么 entitlement 不能代替用户授权？举一个两者都需要的能力。
  2. “发布包残留调试能力”会带来什么风险？
  3. 如果一个功能在开发环境正常、TestFlight 上失败，你会先检查什么？
