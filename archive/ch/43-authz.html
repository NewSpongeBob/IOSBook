S04

身份认证与服务端授权

认证回答“你是谁”，授权回答“你能对哪个资源做什么”

把认证和授权分开，是设计任何账号体系的第一步。而授权必须发生在资源所在的权威端：客户端能表达意图，但不能替服务端做决定。

1. 两个问题，四要素

一次授权判断包含四要素：主体（用户或设备）、资源（哪条数据）、动作（读/写/删除）、上下文（设备、时间、风险）。缺任何一项，判断都会退化成“登录了就能做”。

检查典型实现客户端能代替吗
通道与会话有效令牌校验、会话状态不能，需服务端验签
功能级权限角色、订阅等级不能
对象级权限资源归属校验不能，客户端不知道全量关系
字段级输出按权限裁剪响应不能，裁剪必须在服务端

对象级权限缺失是最常见的真实缺陷：接口校验了“已登录”，却没有校验“这条记录属于你”。表现是改一个 ID 就能读别人的数据。

2. 会话与令牌

  • 短期访问令牌 + 受限刷新凭据：降低泄漏后的可用窗口。
  • 绑定：令牌可绑定设备指纹或会话标识，但要能解释“误绑”的用户体验代价。
  • 撤销：注销、改密、设备丢失必须在服务端失效，不能只清本地。
  • 并发会话：明确允许多设备同时登录还是一处登录踢掉其他，并把策略写进产品行为。

3. 客户端的正确职责

按状态码分流，而不是全局弹登录
switch response.statusCode {
case 200...299:
    break
case 401:
    // 会话失效：尝试一次刷新，失败则回到未登录态
    try await session.refreshIfPossible()
case 403:
    // 权限不足：不要重试，提示或隐藏该操作
    presentPermissionDenied()
default:
    break
}

区分 401 与 403 很重要：前者是身份问题，可以尝试刷新；后者是权限问题，重试无意义。把两者合并处理，会导致“刷新风暴”或“该提示权限时反复弹登录”。

4. 常见误区

  • 隐藏按钮等于授权：界面隐藏只影响正常路径，接口仍可被直接调用。
  • 用客户端角色字段判定：角色值可被改写，必须以服务端记录为准。
  • 只验签名不验声明：令牌需要校验签发者、受众、有效期与权限范围。
  • 把设备标识当身份：设备标识可被重置或伪造，只能作为信号。
  • 客户端缓存授权结论：权限变更后旧结论仍生效，形成越权窗口。

5. 验证清单（自有服务）

  1. 用 A 的凭据访问 B 的资源，确认被拒绝且不泄露资源是否存在。
  2. 降级账号后立刻重试操作，确认权限变更即时生效。
  3. 注销后复用旧令牌，确认服务端已失效。
  4. 检查接口响应是否包含超出当前权限的字段。
  5. 确认 401/403 的处理不会造成无限重试。
