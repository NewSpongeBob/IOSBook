自动化：XCUITest 与 WDA

自动化负责“把路径走一遍”，不负责“看见内存”

XCUITest 与被测应用是两个进程：测试进程通过辅助功能接口点击、输入、截图，不注入、不读内存。它适合把功能路径稳定跑通，再配合日志与断点做定位。

1. 两种形态

形态运行方式适用
XCTest UI 测试Xcode 内置，测试进程驱动应用本地回归、自有应用
WebDriverAgent设备上跑一个 HTTP 服务（默认 8100），外部脚本发请求远程批量、跨语言脚本

2. 能力边界

能做不能做
点击、滑动、输入、截图读取对象内存、调用任意方法
断言界面元素与层级绕过权限或签名限制
稳定复现同一条路径替代断点做调用级观测

所以自动化与插桩是互补关系：前者保证“每次都走到同一个地方”，后者负责“到了之后看什么”。

3. 定位元素

  • 优先用 accessibilityIdentifier：文案会变，标识相对稳定。
  • 元素层级变化会让基于下标的定位失效，尽量按标识或类型 + 标识组合。
  • 系统弹窗（权限、更新提示）会打断流程，先写统一处理再谈用例。
Swift：按标识查找并点击
let app = XCUIApplication()
app.launch()
let login = app.buttons["login.submit"]
XCTAssertTrue(login.waitForExistence(timeout: 5))
login.tap()

4. 与分析的配合

  1. 用自动化稳定触发目标功能（例如进入列表页并下拉刷新）。
  2. 在固定位置下断点或打日志，观察参数与返回值。
  3. 把“某次操作 → 某些调用”的对应关系记下来，形成路径表。
  4. 改动代码后重跑同一用例，确认行为差异。

5. 失败分流

现象原因查哪里
元素找不到标识缺失或层级变化打印元素树，补标识
点了没反应元素存在但不可交互等待可点击状态
随机失败动画、网络、异步加载加显式等待，去掉固定 sleep
权限弹窗卡住系统弹窗不在应用层级统一处理或预置权限
只能模拟器跑签名或设备限制核对测试构建与设备
