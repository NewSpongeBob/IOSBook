WebView 与内容信任边界

WebView 的风险不在“用了网页”，而在“网页能碰到什么”

WebView 同时连着互联网内容和原生能力。判断它是否安全，要看三件事：允许加载什么、页面能调用哪些原生接口、数据在 Web 与原生之间如何流动。

1. 风险模型

面问题控制
内容来源是否只加载自有域名？域名白名单、禁用任意导航
导航重定向、外部链接、自定义 scheme在决策阶段拦截并显式处理
脚本桥页面能调用哪些原生方法？最小接口、参数校验、来源校验
存储Cookie、本地存储是否与其他内容隔离独立数据存储、退出清理
原生能力摄像头、定位、文件是否被页面间接触发权限仍由原生侧按用户意图申请

2. 导航白名单

Swift：只允许业务域名，其余交给系统浏览器
func webView(_ webView: WKWebView,
             decidePolicyFor action: WKNavigationAction,
             decisionHandler: @escaping (WKNavigationActionPolicy) -> Void) {
    guard let url = action.request.url else { return decisionHandler(.cancel) }
    if allowedHosts.contains(url.host ?? "") {
        decisionHandler(.allow)
    } else {
        UIApplication.shared.open(url)   // 外部链接交给系统
        decisionHandler(.cancel)
    }
}

白名单要包含实际用到的主域与必要子域，而不是用后缀匹配（hasSuffix 会让 evil-example.com 通过）。同样要拦截自定义 scheme，避免页面借 URL 触发原生动作。

3. 脚本桥的安全边界

  • 只暴露业务必需的方法，参数按不可信输入校验类型与范围。
  • 桥接消息要能判断来源页面，不能只看消息内容。
  • 不把令牌、密钥等敏感值注入页面脚本；需要时通过一次性、短时效的凭据交换。
  • 注入脚本前评估页面是否可能被第三方内容影响（广告、用户生成内容）。

4. 数据与身份

WebView 的 Cookie 与本地存储等同凭据载体。设计上要明确：登录态存在哪一侧、退出时如何同时清理、是否与非 WebView 的会话共享。共享越方便，越容易被跨站内容利用。

5. 测试用例

  1. 让页面跳转到不在白名单的域名，确认被拦截且没有静默加载。
  2. 构造 javascript: 与自定义 scheme 的链接，确认不会触发原生动作。
  3. 向桥接接口发送超长、类型错误、缺字段的消息，确认拒绝且不崩溃。
  4. 退出登录后检查 Cookie 与本地存储是否被清理。

6. 维护

WebView 相关缺陷常随内容变化出现：运营配置了新域名、接入了新的第三方页面、增加了新的桥接方法。把它们纳入发布检查与回归清单，而不是上线后靠用户反馈发现。
