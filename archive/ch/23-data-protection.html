文件保护与设备锁定状态

文件保护类决定“设备锁定时文件还能不能被读”，这是与加密密钥绑定的系统策略

文件保护把每个文件的解密密钥与设备状态绑定：设备锁屏、密码是否已解锁、密钥是否已派生，共同决定某次读取会不会成功。它不是应用自己做的加密，而是系统在 I/O 层施加的策略。

1. 保护类与设备状态

保护类密钥可用条件典型用途
完全保护设备已解锁高敏感数据，后台不应访问
仅解锁时（除非已打开）解锁后可继续访问已打开的文件需要持续写入的敏感文件
首次解锁前不可用设备本次启动后至少解锁过一次后台任务需要访问的数据
无保护始终可用不含敏感信息的资源，慎用

保护类越严格，后台与锁屏场景的可用性越差。设计时应先列出“谁在什么状态下读这份数据”，再选保护类，而不是统一取最严格或最宽松。

2. 与 Keychain 的区别

  • 文件保护：作用于文件，读不到时返回权限错误。
  • Keychain 可访问性：作用于凭据条目，除了设备锁定状态，还可附加“仅本设备”“需要生物识别”等条件。

两者可以配合：文件里存密文，密钥放在钥匙串；锁屏时钥匙串条目不可用，文件即使被读到也无法解密。这样即使保护类选得宽松，也有第二道保护。

3. 备份与迁移

备份会带走部分数据，某些可访问性属性在恢复后行为不同。“仅本设备”类条目通常不会随备份迁移，这既是安全特性也是产品约束：换机后需要重新登录。

设计检查点：

  • 哪些数据必须跟随用户到新设备，哪些必须留在本机？
  • 恢复后首次启动能否正常走完引导流程，而不是卡在“等待某个密钥”上？
  • 退出登录时是否清除了不应保留的本地副本？

4. 可验证实验（自有设备）

  1. 分别用“完全保护”与“首次解锁前不可用”写入文件，锁屏后尝试读取，记录错误码与调用栈。注意：必须在真实设备上验证，模拟器不体现这套密钥状态。
  2. 在后台任务中读取两类文件，观察是否出现“前台成功、后台失败”的差异。
  3. 把同一份敏感数据分别放在容器文件与钥匙串条目中，比较锁屏、重启、备份三种场景下的可用性。
写入时指定保护类
let url = documents.appendingPathComponent("token.bin")
try data.write(to: url, options: [.atomic, .completeFileProtection])
// 其他选项：.completeFileProtectionUnlessOpen / .completeFileProtectionUntilFirstUserAuthentication

5. 常见误区

  • “文件放在沙盒里就安全了”——沙盒限制其他应用访问，但不阻止设备被解锁后的本地读取。
  • “加密一次就够”——密钥生命周期、备份、迁移都会改变威胁模型。
  • “错误只可能是路径问题”——EPERM 常常来自保护类未解锁，而不是路径错误。
