B02

二进制观测工具与证据记录

工具只提供视图，结论需要坐标系、版本与可重复步骤

观测二进制不是“跑一条命令看输出”，而是回答三个问题：这是什么文件、它依赖与导出了什么、它的来源与完整性如何。每条结论都要能说明用了哪个工具、什么版本、对哪份产物。

1. 三个观察面

面回答的问题常用工具
结构文件类型、架构、段与加载命令file、otool、dyld_info
符号导出了什么、还缺什么、有无调试信息nm、dwarfdump
来源与完整性谁签的、权限声明是什么、是否被改动codesign、shasum

三面互相校验：只看符号会漏掉签名信息，只看签名会漏掉依赖异常。观测顺序建议从结构到符号再到签名，因为后两者的解读依赖前者的坐标系。

2. 一组可复用的命令

对自己构建的产物做基础观测
file /path/to/YourApp.app/YourApp
otool -hv /path/to/YourApp.app/YourApp          # 文件头与架构
otool -L /path/to/YourApp.app/YourApp          # 依赖
nm -m /path/to/YourApp.app/YourApp | head -20  # 符号表与类型
codesign -dvvv /path/to/YourApp.app 2>&1       # 签名与标识
shasum -a 256 /path/to/YourApp.app/YourApp     # 产物哈希

记录产物哈希很重要：同一版本号的不同构建，内容可能不同。没有哈希，后续所有对比都缺少锚点。

3. 证据记录模板

  1. 目标：要验证的假设（例如“Release 构建剥离了调试符号”）。
  2. 产物：路径、构建号、SHA-256。
  3. 环境：工具链版本、系统版本、架构。
  4. 命令与原始输出：保留可复制的原文，而不是转述。
  5. 结论与限制：这条输出能支持什么、不能支持什么。

4. 常见误读

  • “有未定义符号就说明有问题”——动态链接的程序本来就有未定义符号，运行时由依赖提供。
  • “strings 里出现某个词就代表有该功能”——字符串可能来自资源、日志模板或第三方库。
  • “符号被剥离等于混淆”——发布构建剥离调试符号是常规做法，与代码混淆是两件事。
  • “依赖列表里有系统库就说明被使用”——弱链接或间接依赖都可能出现在列表里。

5. 可验证实验

  1. 对 Debug 与 Release 产物各跑一遍上述命令，列出差异（符号、依赖、体积），并解释每一项差异的构建原因。
  2. 把同一份源码分别构建为单一架构与通用二进制，用 file 与 otool -hv 的结果说明差异。
  3. 为自己的观测流程写一份记录，让另一位同事仅凭记录就能复现同一输出。

自测

  1. 为什么必须先记录产物哈希，再谈论符号与依赖？
  2. “未定义符号”在什么情况下是正常的？在什么情况下是缺陷？
  3. 一条工具输出升级为“结论”需要补充哪些信息？
